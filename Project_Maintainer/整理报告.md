# 工程整理阶段报告

日期：2026-09-30
范围：STM32F407 舵轮底盘工程源码与 MDK-ARM 工程配置初查

## 结论

工程按应用层、板级支持、组件、HAL/FreeRTOS、中间件和 UI 分层，Keil 工程显式维护源码分组及编译选项。本轮完成一项有直接引用证据的冗余清理；没有移动源码，也没有调整编译配置或运行逻辑。

## 工程基线

- 目标器件：STM32F407IGHx；工程使用 ARMCC 5.06 Update 7，FreeRTOS/CMSIS-RTOS 和 STM32F4 HAL。
- 启动流程：`Src/main.c` 初始化 HAL、系统时钟及外设，随后初始化 CAN 过滤、延时、校准参数、遥控器、串口和视频传输模块，再启动调度器。
- 任务入口：`Src/freertos.c` 创建测试告警、消息、IMU、LED、OLED、底盘、裁判系统、舵机、空闲和 UI 等任务；底盘/云台任务受板型宏控制。
- Keil 工程文件：`MDK-ARM/standard_tpye_c.uvprojx` 收录应用、BSP、组件、HAL、FreeRTOS 和 USB 源文件，并配置头文件搜索路径、宏和 ARMCC 编译选项。
- 当前源码宏：`application/robot_param.h` 启用 `Hero_robot` 与 `steering_wheel`；`application/remote_control.h` 启用 `chassis_board`。`Infantry_robot` 和 `gimbal_board` 当前未启用。

## 已完成清理

- 删除 `application/test_task.h`，并移除 `application/test_task.c` 对它的引用。该头文件没有声明或定义，只转引 `struct_typedef.h`；唯一包含它的源文件随后直接包含 `detect_task.h`，而后者已包含 `struct_typedef.h` 并提供 `error_t` 等本源文件所需类型。该头文件未单独列入 Keil 工程。
- 保留 `test_task` 实现及任务创建。应用层实现负责检测离线错误并驱动蜂鸣器，属于实际任务行为，不能因名称含“test”而删除。

## 待确认与疑点

- **车型配置差异**：用户描述为舵轮步兵，但当前配置启用 `Hero_robot`，步兵参数宏处于注释状态。两套宏对应不同底盘尺寸、轮位和控制参数；需要先确认实际车型，不能直接切换。
- **Keil 宏重复**：`uvprojx` 的 `Define` 字段重复列出 `USE_HAL_DRIVER` 和 `STM32F407xx`。虽然看起来重复，但本轮不调整编译配置；应在 Keil 可用时先核实工程目标和构建结果。
- **生成任务框架**：`freertos.c` 有弱 `test_task` 占位实现，应用层又提供同名强实现；`testHandle` 只接收任务创建返回值，未见读取点。它们位于生成的 FreeRTOS 框架文件，本轮保留，避免改写生成代码或任务创建路径。
- **配置选项注释**：`robot_param.h` 中未启用的兵种/底盘宏是显式配置选项，不视为死代码。
- **文档与源码不一致**：根目录 `readme.md` 仍描述麦轮/X 型底盘，与当前舵轮宏不一致。需确认 README 是否仍作为本项目使用说明，再更新相关文档。
- **目录结构**：应用、BSP、组件、HAL 和中间件已有职责边界。本轮没有足够证据证明移动文件能改善结构，且移动会牵涉 Keil 路径和分组，因此暂不调整目录。

## 后续计划与预期

1. 确认当前固件对应的车型及主控板类型，再审查 `robot_param.h`、板型宏和相关条件编译路径。
2. 按 `uvprojx` 的实际收录清单核对磁盘源码；结合普通调用、宏分支、中断入口、HAL 回调、函数指针和弱符号逐项验证候选项。
3. 优先清理已证明未引用且不属于生成框架的文件、声明和重复实现；任何源文件移动都同步更新 Keil 分组、路径及相关配置。
4. 每组改动独立检查；在可用的 MDK-ARM/ARMCC 环境执行完整构建，并核对构建输出。硬件相关行为仍需在目标板上验证 CAN/UART/DMA、中断、任务调度及初始化时序。
